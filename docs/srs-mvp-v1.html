Executive Summary

This document converts the approved Stage 1 product scope into 124 functional requirements across 15 modules, together with business rules, field validations, security and privacy requirements, non-functional targets, error handling, edge cases, and testable acceptance criteria.

Requirements analysis found eight missing areas and two internal contradictions in the approved scope. All ten were resolved with the product owner and recorded in the Stage 2 change log above. Nothing was assumed silently.

The two contradictions found
  • Private profiles without follow approval. SAFETY-011 offered a private-profile toggle while the follow-approval mechanism was explicitly out of scope, leaving "private" undefined. Resolved by removing the toggle from MVP.
  • "Public posts" with no visibility control. The Discover feed referred to public posts, but no visibility setting existed anywhere. Resolved by making visibility a profile property that posts inherit, with PUBLIC as the only permitted value in V1.
What this document does not do
  • It does not select a technology stack, framework, database, or hosting provider
  • It does not specify API contracts, schemas, or data models
  • It does not design screens, flows, or visual treatment
  • It does not expand the approved scope — six changes were made, each approved on the record

The requirements are written to be handed directly to a designer, an architect, developers, and QA. Every functional requirement carries acceptance criteria in Given/When/Then form so that it can be turned into a test case without further interpretation.

Product Overview

A bilingual (Urdu and English) civic community platform for Pakistan. Citizens discover awareness content, discuss local issues, connect with each other and with civic organizations, and gather at community events.

The product is a mobilization platform, not an entertainment platform. Its core loop is: awareness content → discussion → connection → participation.

Platform, V1Android application + Admin Web Portal (English-only admin interface)
LanguagesUrdu and English, switchable. Full right-to-left layout for Urdu.
Access modelAuthentication required. No guest browsing.
GeographyPakistan. Registration restricted to Pakistani mobile numbers in V1.
Minimum age13 years, verified by date of birth at registration
Moderation modelPost-moderation. Content publishes immediately; reaching the report threshold auto-hides it; a human administrator makes every permanent decision.
Target scale, year one1,000 registered users · 400 monthly active

Description
A Shehersaaz staff member operating the Admin Web Portal. All administrators hold identical permissions — no hierarchy exists in V1 (ADMIN-015 deferred).
Who qualifies
Accounts are created outside the Admin Portal by the designated technical owner with server access (S2-CR-005). There is no self-registration and no in-portal admin creation.

Can
Review the moderation queue · Restore auto-hidden content · Permanently delete any post, comment, or event · Search and view any user account · Suspend, ban, and reinstate users · Publish announcements to the Featured section · Grant and revoke verification badges · View the dashboard and audit log
Cannot
Act on another administrator's account in any way — no suspension, ban, deletion, or permission change · Create or remove administrator accounts · Read users' direct messages except the specific conversation attached to a report · Edit the content of a user's post — only delete it · Export bulk personal data · Alter or delete audit log entries
Access
Admin Web Portal only, English interface. Administrators have no elevated capability inside the Android application.
Security note on the equal-admin model. Because all administrators are equal, ROLE-003's inability to act on another administrator is what prevents a single compromised account from locking the whole team out. This restriction must be enforced server-side, not merely hidden in the interface. See SEC-021.

10.13Safety, Reporting and Blocking

SAFETY-FR-004Threshold Auto-HideMust
Description
Content that accumulates reports from enough distinct users is hidden automatically and immediately, then queued for a human decision. This is the mechanism that lets a small moderation team run an open platform safely.
Actor
System, triggered by user reports
Trigger
A report is recorded against a piece of content
Preconditions
The content exists and is currently visible
Main flow
  1. System records the report and counts distinct reporting accounts
  2. System compares the count against the threshold for that content type
  3. On reaching the threshold, the content is hidden from all feeds, profiles, and search immediately
  4. The author is notified that their content is under review
  5. The item enters the moderation queue, ordered by report severity then age
  6. An administrator restores it or deletes it permanently (ADMIN-FR-003, ADMIN-FR-004)
Alternate flows
A1 Restored → the content returns to full visibility and its report count resets, so the same reporters cannot immediately re-hide it. A2 Deleted → removal is permanent, and the author may additionally be suspended. A3 The author deletes it before review → the queue entry is closed as resolved.
Error flows
E1 The same user reports the same item twice → the second report is ignored and does not increment the count (BR-030). E2 Two administrators act on the same queue item simultaneously → the first action wins and the second sees the item already resolved, with the acting administrator named (see EDGE-024). E3 Content is deleted between hiding and review → the queue entry closes automatically.
Business rules
Thresholds: Posts 3 distinct reports · Comments 3 · Events 2 · Profiles never auto-hidden · Direct messages never auto-hidden.
BR-030 — one report per user per item; the count is of distinct accounts, never of total reports.
BR-032 — a human always makes the permanent decision. Nothing is ever deleted automatically. This is deliberate: on a civic platform, wrongly deleting a citizen's criticism is worse than briefly hiding it.
BR-037 — if an administrator permanently deletes 3 of a user's items within 30 days, that account is flagged in the queue for a suspension decision. It is not auto-suspended.
