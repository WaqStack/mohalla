UX Executive Summary

This specification converts the approved Product Scope and SRS into a complete, implementable design for an Android-first bilingual civic platform. It covers 61 mobile screens and 9 admin screens, a design system of 91 tokens and 48 components, and every empty, loading, error and interaction state those screens require.

The design thesis

Mohalla — محلہ — "the neighbourhood." This product replaces the WhatsApp group, and a WhatsApp group is not a newsfeed: it is a room full of people you recognise. So identity leads. Faces, names, cities and verified badges are the largest elements on every card. Content sits on warm limestone as distinct objects, the way notices sit on a community board. A single geometric tile — reduced from Sindhi and Multani ceramic tilework — carries the brand structurally: it is the active navigation shape, the verified badge frame, the empty-state anchor and the skeleton pattern. Used for structure, never as ornament.

Six decisions that shaped everything downstream

DecisionRationale
Events get a top-level tabEvents are the mobilization layer and the clearest thing this product does that Facebook does not. Burying the differentiator two levels deep would be a strategic error, not a layout one. Feed and Discover are the same activity — reading posts — so they became sibling tabs inside Home, freeing the slot.
Naskh for interface, Nastaliq for displayNastaliq needs roughly double line-height and fails below 16sp. Naskh shares a workable vertical rhythm with Latin, so both languages can use one spacing system. Nastaliq appears only where it can breathe: the language screen, section headings, empty states.
Identity-forward post cardsOn a platform whose differentiator is credibility, the author must be unmissable. Avatar, name, verified badge and city occupy the top third of every card, and the author row is itself the tap target into their profile.
Three tiers of destructive confirmationDeleting a post, blocking a person and deleting an account are not the same act. They get a sheet, a sheet with mutual-consequence copy, and a dedicated screen with password re-entry respectively.
One neutral unavailable stateBlocked, deleted, banned and not-found all render identically. Any visual difference between them would leak the existence of a block, which BR-025 forbids.
Cold start designed as one systemFeatured, Discover and Suggested Accounts were designed together against seeded sample data, never against lorem. A new user who follows nobody still lands on a populated screen.

What this document does not do

  • It adds no features. Six exclusions were re-confirmed rather than quietly designed in.
  • It changes no business rule, role or permission. Where a rule constrained the design, the design bent.
  • It selects no backend technology, designs no schema, and specifies no API.
  • It does not ship dark mode. Tokens are structured so it can be added later without redesign — recorded as a Phase 2 design-system capability in §15.

Design Goals

IDGoalHow it is measured in the design
DG-01A new user reaches content in under 90 secondsSeven onboarding steps, three of four profile fields optional, persistent step indicator so effort feels finite. No step asks for anything it does not need.
DG-02Urdu is not a second-class experienceEvery screen specified in both directions. Naskh line-heights defined per type token. Nastaliq used deliberately, not decoratively. Language is the first screen, with no pre-selected default.
DG-03The feed is never emptyFeatured renders from admin content regardless of follows. Discover is one tap. Suggested Accounts returns at least ten. Three requirements, one system.
DG-04Trust is visible, not claimedVerified badge appears on profile, every post, every comment, search results and the message inbox. Author identity is the largest element in a post card.
DG-05Safety tools are findable under stressReport is two taps from any content. Reasons are one tap each, in plain language, in the user's own script. Note optional. Block is offered immediately after reporting.
DG-06Destruction is proportionateThree confirmation tiers. Account deletion gets a screen and a password, not a sheet. Every destructive control is visually distinct from its neutral equivalent.
DG-07The app works on a cheap phone on bad dataNo blur, no gradients, no large decorative assets. Skeletons over spinners. Optimistic states with honest reconciliation. Cached content over blank screens.
DG-08Recognisable from a screenshot without a logoLimestone ground, tile-shaped active state, category-tinted chips with a leading accent, circular avatars at a consistent 44px, and a paired Follow/Message button row. Tested against §28's five questions.

Product Design Principles

Eight principles, each with the concrete rule it produces. A principle that does not constrain a decision is decoration.

PrincipleThe rule it produces
1 · People before postsAuthor identity is never smaller than the engagement controls. The avatar is 44px on every card, never 24px. The author row is a tap target, not a caption.
2 · Both languages, one rhythmNo screen may use a spacing value that only works in one language. Urdu line-heights are defined per type token so vertical rhythm survives the switch.
3 · Say what will happenEvery destructive confirmation names the consequence in the user's words. "Delete post" says the comments go too. Account deletion says the posts stay as "Deleted User" — before the user commits, not after.
4 · Never a dead endEvery empty state and every error state carries an action. No screen may terminate in a message with nowhere to go.
5 · Icons are never aloneBottom navigation always shows labels. Any icon-only control carries a content description and, where meaning could be ambiguous, a visible label. Colour is never the sole carrier of meaning.
6 · Cheap to renderNo backdrop blur, no multi-stop gradients, no shadow above elevation 2 in scrolling content. One shadow direction throughout. Skeletons, not spinners.
7 · Structure, not ornamentThe tile motif may only appear where it does a job: active state, verified frame, empty-state anchor, skeleton fill, section divider. It is never wallpaper, never a border pattern, never repeated for texture.
8 · Optimistic, but honestLikes, follows and messages update instantly. When the server disagrees, the interface reverts to the true state and says so. It never leaves a false success on screen.

Selected Visual Direction

Direction B — Mohalla (محلہ) selected. Three directions were developed: Dastavez (editorial record — type-led, ruled, archival), Mohalla (warm neighbourhood — surface-led, identity-forward), and Naqsha (civic structure — grid-led, high-contrast, bold). Mohalla was selected and approved.

Why Mohalla, in four points

ReasonDetail
It matches the actual userThe audience is the general Pakistani public, all ages, all confidence levels, currently coordinating over WhatsApp. Dastavez asks them to read a document. Naqsha asks them to use an institution. Mohalla asks them to join a neighbourhood — and identity-forward, card-based, always-labelled design is the pattern they can already operate.
It makes trust visibleVerified badges, real faces and city context are the largest elements on every card. Dastavez subordinates identity to text; Naqsha subordinates it to structure. On a platform whose credibility is its differentiator, identity must lead.
The tile motif solves distinctiveness honestlyCulturally specific to Pakistan, geometric enough to work as a UI primitive, and used structurally rather than decoratively. It gives the app a screenshot-recognisable signature without resorting to novelty.
It lands all nine target adjectivesModern · premium · clean · social · warm · trustworthy · fast · memorable · intuitive. Dastavez fails "warm" and "social." Naqsha fails "warm." Mohalla lands all nine.

Taken from the rejected directions

  • From Dastavez: typographic discipline and generous line spacing. Urdu needs room, and the type scale reflects that rather than compressing to fit more content.
  • From Naqsha: category coding at a structural level. Colour-coded topics scan faster than text labels alone, so every card carries a category chip plus a 3px leading accent in that category's colour.
The risk being managed. Warm, rounded and card-based is the most common social-app shape, so the motif, the limestone ground and the category system have to carry the differentiation. Applied timidly, this direction drifts toward generic. Three rules prevent that: the tile appears only where it does a job (§13); the ground is limestone, never white, so cards read as objects on a surface; and avatars are a fixed 44px on every card, never shrunk to fit more content.

The core motif — khatam tile

What it is

An eight-point star reduced from Sindhi and Multani ceramic tilework to its simplest geometric form — two overlapping squares, rotated 45°, resolved into a stepped octagonal silhouette. One shape, used at four sizes.

56 · 36 · 24 · 14px

Where it may appear Exhaustive list
  1. Active navigation indicator — filled tile behind the icon
  2. Verified badge frame — 15px tile with a white check
  3. Empty-state anchor — 56px outlined tile containing an icon
  4. Skeleton fill — a faint tile grid at 4% opacity
  5. Section divider — an 8px tile centred in a hairline rule
  6. Featured strip marker — a 14px tile before the label
  7. App icon and splash — the tile is the mark
Nowhere else. Never wallpaper, never a repeating border, never texture, never decoration on a card. Seven jobs, no exceptions. This restraint is what keeps it a signature instead of a theme.

Shape, surface and treatment language

DimensionRule
Shape languageSoft rectangles with one deliberate exception. Cards, sheets, inputs and buttons are rounded. The tile is the only angular form in the system, which is what makes it read as a mark rather than a shape.
Radius philosophyRadius scales with the size of the surface: 8px for chips, 12px for controls, 16px for cards, 24px for sheets, full for avatars. A small element never carries a large radius — that is what produces the over-rounded look this direction avoids.
Surface philosophyContent lives on white surfaces; the app lives on limestone. The ground is never white, so cards read as objects placed on a surface rather than regions of one. Exactly two surface levels — ground and card. No third level, no nested cards.
ElevationOne shadow direction, downward, three levels only. Cards use level 1 and nothing in a scrolling list goes above it. Level 2 is sheets and the Create control; level 3 is modals alone.
Image treatment12px radius, never full-bleed to the card edge — an 8px inset preserves the sense of an object on a surface. No overlays, no gradient scrims, no filters. Awareness posters must be readable, and a scrim over text is unreadable text.
Icon philosophy2px rounded stroke, 24px grid, soft terminals. Outlined by default; filled only for an active navigation state. Small, consistent set — no icon exists unless a screen needs it.
Illustration philosophyEmpty states only. A single tile at 56px containing one 24px icon, plus a headline and an action. No characters, no scenes, no mascots — illustration cost is bytes on an expensive connection.
Divider treatment1px hairline in border-default. Section breaks add an 8px tile centred in the rule. Never a thick rule, never a shadow used as a divider.
Active-state treatmentNavigation uses the filled tile. Tabs use a 2px underline. Chips fill with their category colour. Buttons darken by one step. Every active state also changes a non-colour property — weight, fill, or shape — per NFR-ACC-005.
The screenshot test. A screenshot with the logo removed should still be identifiable by: limestone ground behind white cards · the filled tile active state in the bottom bar · 44px circular avatars with a tile-framed verified badge · category chips with a matching 3px leading accent · and the paired Follow / Message button row on profiles. Five signatures, none of them decorative.

Nothing loops forever and nothing must be waited through. Tokens onlyNo hardcoded colour, size, radius, spacing or duration anywhere. If a value is needed that is not a token, that is a design question, not an implementation decision.
Both directions, from screen oneBuild every screen in LTR and RTL before moving to the next. Use logical properties — start/end, not left/right — throughout.
48dp minimum, alwaysVisual size may shrink; the target may not. Verify with a touch-target overlay, not by eye.
Server is the authorityOptimistic UI is a courtesy. Every state reverts to the server's answer, and the user is told when it does (Principle 8).
One unavailable stateDeleted, hidden, blocked and banned share one component, one string, one icon, one action. Do not branch it.
Skeletons match geometryA skeleton whose dimensions differ from the real content causes layout shift, which is worse than a spinner.
No new iconsThe icon set is closed. A screen needing an icon that does not exist is a design question.
Copy is finalEvery string in §20, §22 and §27 is approved copy pending Urdu translation (OD-016). Do not paraphrase — several strings are worded specifically to avoid leaking information.
